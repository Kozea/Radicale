# Architecture

Radicale is a WSGI application that speaks CalDAV, CardDAV, and a small HTTP API. One process loads a configuration and a set of plugins, then handles each request inside that process. There is no separate database server. Collections live on the filesystem. See [data-model.md](data-model.md).

## Processes

Two entry points build the same `radicale.app.Application`.

* `radicale` (console script `radicale.__main__:run`) parses the command line, loads config, and either runs one of the verify flags below or calls `radicale.server.serve`.
* `radicale.application` is the WSGI callable for an external server. It reads `RADICALE_CONFIG` from the WSGI environ, then from the process environment. The first call builds one `Application` and caches it. A later call with a different `RADICALE_CONFIG` raises `ValueError`.

`server.serve` looks at `[server] type`:

| Value | Module | What it speaks |
| --- | --- | --- |
| `builtin` (default) | `radicale.server` | HTTP/1.0 through `wsgiref`. The connection closes after each request. |
| `hypercorn` | `serve_hypercorn` in `radicale.server` | HTTP/1.1 and HTTP/2, including cleartext HTTP/2 (H2C). Optional extra `h2`. |
| `cheroot` | `radicale.server_cheroot` | HTTP/1.1 with keep-alive. Optional extra `cheroot`. |

`[server] hosts` is used by these three servers. An external WSGI server ignores it and binds the socket itself.

`--verify-storage` loads storage and exits. `--verify-sharing` loads sharing and exits. `--verify-item` calls `item.verify` on one file and does not load those plugins. None of the three calls `serve`.

## Plugins loaded for every application

`Application` is a class built from one mixin per HTTP method, on top of `ApplicationBase`. `ApplicationBase.__init__` loads, in order:

1. `radicale.auth`
2. `radicale.group`
3. `radicale.storage`
4. `radicale.rights`
5. `radicale.web`
6. `radicale.sharing`
7. `radicale.hook` (an import or constructor failure is logged; the loader copies the configuration and sets the hook type to `none` on the copy. The application's configuration keeps the type that failed)

`utils.load_plugin` imports `radicale.<section>.<type>` when `type` is one of that package's `INTERNAL_TYPES`. Any other string is treated as a Python module path. The module must define the class named in the `load_plugin` call (`Auth`, `Group`, `Storage`, `Rights`, `Web`, `Sharing`, or `Hook`). `load_plugin` does not check that the class subclasses the matching `Base*` class. It calls that class with the configuration.

`BaseSharing.__init__` loads rights, storage, and group again. Those are separate instances from the ones on `Application`. It does this even when both sharing features are off. When both `collection_by_map` and `collection_by_token` are false, it sets itself disabled and returns before `_init_db`, so it calls neither `database_init` nor `database_get_info`. `verify` still calls `_init_db`, including from `--verify-sharing`.

Configuration is a `radicale.config.Configuration`. The application's configuration object is not mutated for the life of the process. The hook fallback copies that object and changes the hook type on the copy. Sections in the reference file `config` are `server`, `encoding`, `auth`, `group`, `rights`, `storage`, `sharing`, `web`, `logging`, `headers`, `hook`, and `reporting`. Option types and defaults live in `radicale/config.py` (`DEFAULT_CONFIG_SCHEMA`). The reference `config` file comments the defaults operators see.

## Request path

`Application.__call__` is the WSGI entry. It logs and turns an uncaught exception into HTTP 500. `HEAD` returns no body.

`_handle_request` then:

1. Sanitizes `PATH_INFO` with `pathutils.sanitize_path`. `reverse_proxy` becomes true when `HTTP_X_FORWARDED_FOR`, `HTTP_X_FORWARDED_HOST`, `HTTP_X_FORWARDED_PROTO`, or `HTTP_X_FORWARDED_SERVER` is present and non-empty. An empty value leaves it false. The path prefix is removed only then, and only when the sanitized path starts with it. When `reverse_proxy` is true and `[server] script_name` is set, that option is the prefix. Otherwise the prefix is `HTTP_X_SCRIPT_NAME` when that key is in the environ, including when its value is empty. `SCRIPT_NAME` is used only when that key is absent.
2. Rejects a path that fails the path check. The configured value is `[server] validate_path_value`. If storage does not support Unicode and that value is not already `strict` or `no-unicode`, the application forces `no-unicode`. `strict` uses `PATH_PATTERN_STRICT_RE` (`re.search` of a pattern that ends in `$`). Python `$` also matches before one trailing newline, so a path such as `/foo\n` passes `strict`. Every other mode uses `_check_format`, which rejects that newline as an ASCII control (`c <= chr(31)`, or `127` through `159`), rejects Unicode category `C`, and rejects a trailing space when the storage cannot store one.
3. Looks up `do_<METHOD>`. Unknown methods are HTTP 405. The methods are `DELETE`, `GET`, `HEAD`, `MKCALENDAR`, `MKCOL`, `MOVE`, `OPTIONS`, `POST`, `PROPFIND`, `PROPPATCH`, `PUT`, and `REPORT`. Each `do_*` is on the mixin in `radicale/app/<method>.py`.
4. Redirects a path to `base_prefix + "/"` with 301 when `path.rstrip("/")` ends in `/.well-known/caldav` or `/.well-known/carddav`. A trailing slash is included, so `/.well-known/caldav/` and `/.well-known/carddav/` are 301 too. Any other `/.well-known` path is 404. This runs before authentication.
5. Authenticates. `remote_user`, `http_remote_user`, and `http_x_remote_user` implement `get_external_login` as `return environ.get(name, ""), ""`. That 2-tuple is truthy even when the header is missing, so HTTP Basic is not read. The handler applies `login or ""` only in that external-login branch. Every other auth type returns `()`. That `()` is falsy, and the handler decodes HTTP Basic only when `HTTP_AUTHORIZATION` starts with `Basic`. With no header, or any other scheme, `login` stays empty. Step 9 then runs `do_*` as anonymous, except a free-busy view that is not `GET` or `HEAD`. `Auth.login` returns `(user, groups, info)`, where `info` is the auth type string, with `/cached` appended on a cache hit. After a failed login the handler sleeps for `[auth] delay` when that value is greater than 0: the fixed delay when `PYTEST_VERSION` is in the environment, otherwise `delay * (0.5 + random.random())`. `BaseAuth.login` calls `_sleep_for_constant_exec_time` when the username is empty after `lc_username`, `uc_username`, `urldecode_username`, and `strip_domain`, and when a backend failure reaches the end of `login`. A failed-login cache hit returns before that pad. The pad is not the `delay` option. An unsafe username clears `user` and leaves `login` set, so step 7 does not run and `do_*` is not called. Step 8 can still return 413 when `[server] _internal_server` is true, `[server] max_content_length` is greater than 0, and `CONTENT_LENGTH` is above that limit. That return never becomes a 403. On `hypercorn`, a buffered body longer than that limit is 400 from the WSGI wrapper and never reaches step 8. When step 8 does not return, the result for that unsafe username is `httputils.NOT_ALLOWED` (HTTP 403, body `Access to the requested resource forbidden.`). Step 10 may rewrite that 403 to 401. A path that starts with `/.token`, and a truthy `get_external_login`, stay 403.
6. When `user` and `login` are set and `[group] type` is `htgroup`, replaces the group set from the group plugin. `from_auth` keeps the groups `Auth.login` returned.
7. When `user` is set and `/{user}/` is missing, calls `rights.authorization` for that path before `do_*`. If the result contains `W`, creates the principal. `[storage] predefined_collections` are created only after that new principal exists. A `ValueError` while creating one predefined collection is logged and the request continues. A `ValueError` or `OSError` while creating the principal returns 500. If `W` is absent, the request logs a warning and continues. An existing principal does not call `authorization` here.
8. When `[server] _internal_server` is true and `[server] max_content_length` is greater than 0, the application rejects a `CONTENT_LENGTH` above that limit with 413. `server.serve` copies the configuration and sets that flag before it chooses `builtin`, `hypercorn`, or `cheroot`. `builtin` and `cheroot` reach that 413. `serve_hypercorn` also sets Hypercorn `wsgi_max_body_size` to the same limit, or to `sys.maxsize` when the limit is 0. Hypercorn 0.17.3's WSGI wrapper answers 400 and does not call the application when the buffered body is longer than that size. An external WSGI server does not set `_internal_server`, so the application's check does not run there.
9. Calls `do_<METHOD>` only when `login` is empty or `user` is set. A free-busy view (`requests_freebusy_view`) allows only `GET` and `HEAD`.
10. If the result is `httputils.NOT_ALLOWED` and `user` is empty, the status becomes 401 and the header is `WWW-Authenticate: Basic realm="<auth realm>"`, except when the path starts with `/.token` or `get_external_login` returned a truthy value. `()` is falsy, so Basic auth is still rewritten. The remote-user 2-tuple, including `("", "")`, is truthy, so that 403 is kept. The body stays `Access to the requested resource forbidden.`

`GET` of the root redirects to `base_prefix + "/.web"` with the default 302. That target has no trailing slash. With `[web] type = internal`, `GET /.web` (and `HEAD`, because it calls `GET`) then 302s to `base_prefix + "/.web/"` because `internal_data` is a directory.

XML bodies are parsed with `defusedxml`. A string response body is encoded first. The body, whether it arrived as a string or as bytes, is then compressed with zstd when `from compression import zstd` succeeded and a comma-separated `Accept-Encoding` token, after stripping, is exactly `zstd`. Otherwise it is gzip when a token is exactly `gzip`. `gzip;q=1.0` does not match. If neither exact token is present, compression does not set `Content-Encoding`. `[headers]` are copied on after that. A config file is read with `RawConfigParser`, which lowercases names, so a file entry `Content-Encoding` is stored as `content-encoding`. That adds a second header and does not replace the `Content-Encoding` key compression just set. A command-line `--headers-Content-Encoding` keeps that spelling, and the copy then replaces the key.

Rights are not a separate proxy. The `OPTIONS`, `POST /.web`, and `GET /.web` handlers do not call `authorization` themselves. A logged-in request whose `/{user}/` principal is missing still calls it in step 7, before those handlers. `do_POST` itself does not call `authorization`. `POST /.web` does not. A `POST` that is neither `/.web` nor `/.sharing` does not. `POST /.sharing` is handled by `sharing.post`, which builds `Access` for create and for several updates, and `Access` calls `authorization`. `GET`, and `HEAD` because it calls `GET`, redirects the root and serves `/.web` before it builds `Access`. `GET /.mobileconfig` returns `httputils.NOT_ALLOWED` when `user` is empty, so no profile is built. When `user` is set it builds the profile and does not call `authorization`. The other `do_*` methods that authorize a collection build `Access` in `radicale/app/base.py`, which calls `authorization`, or call `authorization` themselves. Some return `NOT_ALLOWED` before that. A `DELETE` of a share whose `PathMapped` ends with `/` is one of those. The letters are documented in the module docstring of `radicale/rights/__init__.py` and in [DOCUMENTATION.md](../DOCUMENTATION.md).

## What a method is allowed to touch

A collection create, upload, or delete takes `storage.acquire_lock` with mode `"w"`. The lock file for `multifilesystem` is `.Radicale.lock` under the storage folder. A read takes mode `"r"`. Cache, history, and sync-token files can still be written while that mode is `"r"`, or after the read lock is released. [data-model.md](data-model.md) lists those writes. A collection `DELETE` calls `hook.notify` inside that write lock, after the storage change, once per item `get_all()` yields, when `hook.enabled` is true. A member that `get_all()` does not yield is not notified. That includes a broken member omitted while `[storage] skip_broken_item` is on. A `DELETE` of one member notifies that member, also inside the write lock and only when `hook.enabled` is true. An empty collection does not call `notify`. A member `PUT` is a `PUT` of a path that is not already a collection, under a parent whose tag is non-empty. An existing collection, and a parent with an empty tag, are whole-collection `PUT`s. `prepare` runs before the lock with no tag and no whole-collection flag. That call treats the body as a whole collection when the path has `W` or `w` and the parent has no `w`, and predicts with `predict_tag_of_whole_collection`. It treats the body as a member, and predicts with `predict_tag_of_parent_collection`, only when the path has neither `W` nor `w` and the parent has `w`. `do_PUT` returns `NOT_ALLOWED` before the first `prepare` when the path has neither `W` nor `w` and the parent has no `w`. If the path has `W` or `w` and the parent also has `w`, the first `prepare` does not classify the request and does not append. Inside the lock, `prepare` runs again only when the lock's tag or whole-collection flag differs. That second call receives those values. When the second call is a member, the flag passed to `prepare` is false and the parent has `w`, so that call keeps the parent tag and does not predict. `do_PUT` reaches that second call only when the first `prepare` returned and the parent has `w`. On a member path whose parent has no `w` and whose own path has `W` or `w`, the first `prepare` takes the whole-collection branch. If that call returns, `do_PUT` returns `NOT_ALLOWED` before the second `prepare`. If `predict_tag_of_whole_collection` returns no tag, the first call raises `ValueError` (`Can't determine collection tag`) outside its `try`, and the handler answers 500. A whole-collection path does not use the parent-`w` test. When `write_whole_collection` is true, `prepare` always replaces the tag with `predict_tag_of_whole_collection`. A member append happens only in the call whose tag is `VCALENDAR` or `VADDRESSBOOK` after `check_and_sanitize_items` returns. `VSUBSCRIBED` passes the allowed-tag test. On a member, a component count other than one raises first, and one component then raises `ValueError` in the final branch, so the request returns 400 and does not append. A UID conflict returns 409 before `upload`. After `upload` succeeds, `notify` runs when `hook.enabled` is true. A `ValueError` from `upload` returns before `notify`. No whole-collection `PUT` calls `hook.notify`. `prepare` fills the iterator for a whole-collection `VCALENDAR` or `VADDRESSBOOK`, and `create_collection` consumes it before the `notify` loop. A whole-collection `PUT` of any other tag never fills the iterator. `PROPPATCH` notifies only when the body parsed as XML. A share-overlay `PROPPATCH` returns before that method's own `acquire_lock`. It updates the share row and does not call `set_meta` or `hook.notify`. The `csv` backend always takes a storage write lock inside `database_update_sharing`. The `files` backend returns `not-found` before that lock when the share file is missing, and takes the lock when the file exists. `[storage] hook` runs after that caller returns normally and before the write lock is released. It does not run when the locked block raises. An unknown `%` placeholder is logged and the command is not started. A bad conversion of a known name, such as `%(path)d`, is not caught there and propagates. `[storage] hook` is a shell command, described in [data-model.md](data-model.md). Sharing overlays and token paths are applied inside the method mixins and `radicale.sharing`, not by a second server.

The web UI is not a separate service. `[web] type = internal` serves `radicale/web/internal_data/` from the `Web` plugin, except `/.web/js/config.js`, which is generated from `[web] prefer_browser_login`. `[web] type = none` still answers `GET /.web` with the text `Radicale works!`. That body is a string, so the sent `Content-Type` is `text/plain; charset=` plus `[encoding] request`.
